- [x] **Migrate scroll-reveal to `IntersectionObserver`** — [scroll-animation.js](src/utils/scroll-animation.js) currently attaches an un-throttled `scroll` listener that runs on every scroll tick and toggles classes on *all* `.scroll-animate` elements each time. `IntersectionObserver` is the modern, jank-free standard for this exact pattern and avoids the main-thread cost entirely. — **Done**: replaced the `scroll` listener + `getBoundingClientRect()`-per-tick loop with a single `IntersectionObserver` (`threshold: 0`, `rootMargin: "0px 0px -20% 0px"` to approximate the old reveal point) that toggles `is-visible` via `entry.isIntersecting`, preserving the original reveal/hide-on-scroll-back behavior. - [ ] **Only if more responsive `<picture>` images get added elsewhere on the site — extract the srcset width list into a shared build-time config.** [index.html](index.html)'s hero `<picture>` (added via [scripts/generate-hero-variants.mjs](scripts/generate-hero-variants.mjs)) currently hand-repeats the same 6-width list (640/828/1080/1440/1920/2560) three times — once per `<source>`/`<img>`. Not worth extracting for a single image, but if a second responsive image shows up (e.g. fleet or services photos), pull the width/format list into one shared config that both the sharp-generation script and the HTML-building step read, so it's defined once. **Must stay a build-time step** — a Node script that writes the fully expanded `srcset="...640w, ...828w, ..."` into static HTML, same pattern as the current generation script — never a JS constant shipped to the browser that sets `srcset` at runtime. Client-side srcset assignment would hide the image from the browser's preload scanner (which only sees raw parsed HTML before JS runs), delaying load of an `loading="eager" fetchpriority="high"` image and hurting LCP — a Core Web Vital and Google ranking factor — plus making the image less reliably picked up by search-engine indexing than if it's present in the initial static markup.
